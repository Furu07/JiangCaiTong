# P2C 798 验证码登录

验证日期为 2026-11-09，版本为 0.5.0 Debug。

| 环节 | 证据与结果 |
| --- | --- |
| 错误来源 | 0.4.0 的通用业务错误会直接显示响应 `msg`，应用没有原样硬编码用户所报的“验证码错误或失效”。代码支持该提示来自平台响应的判断，仍缺该次 HTTP 状态和业务码。 |
| 协议对照 | 发送和提交使用同一设备账号通道 `1,1`。接口路径、客户端版本、JSON 字段和登录签名与本地航院通 Android 源码一致。测试确认短信验证码以字符串提交并保留前导零。应用商店版本信息不足以证明服务端协议已变更，本轮保留请求版本和字段。 |
| 已修正缺口 | 上游 Android 的 HTTP 客户端会保留响应 Cookie，旧版酱菜通的 798 登录请求之间没有 Cookie 容器。新版按每次短信操作建立独立的临时 Cookie 容器，提交时仅沿用同一手机号和短信操作对应的容器。容器只用于 798 登录端点，与学习通及查询请求隔离。并发、换号和无本次短信会话会被拦截。 |
| 错误和诊断 | 区分短信错误、过期、服务端无法区分的拒绝、会话不匹配、参数问题、服务器拒绝和平台成功但本地保存失败。Debug 面板只保留本次运行的阶段、HTTP 状态、可用数字业务码、分类、会话布尔值、耗时和异常类型。 |

`node tests/water-login.test.cjs` 的定向测试通过。MuMu 上用合成 Cookie 验证同一次短信操作可在提交时读取 Cookie，其他操作和余额查询不能复用。**缺失 Cookie 是已确认的实现差异，该差异是否触发此次真实故障尚未证实。** 未自动发送短信或提交验证码。

用户已完成一次 0.5.0 手动验证。短信接口返回 HTTP 200、业务码 `0`，登录接口返回 HTTP 200、业务码 `-1`，应用归类为一般业务拒绝。两次请求均没有可记录的 Cookie 发送或留存，旧诊断无法判断响应头是否带有 `Set-Cookie`。上游历史记录中缺少签名和签名无效也都曾返回 `-1`，因此该码无法区分验证码、签名或其他服务端限制。

0.5.1 对无法归类的拒绝显示业务码及“原因未能识别”。Debug 只增加响应头存在布尔值与命中的错误字段名，无错误原文或凭据。模拟测试覆盖一般拒绝、备用错误字段、响应头存在与否及脱敏。保持现有协议参数，未再次发短信或登录。真实故障根因及修复结果仍待确认。
